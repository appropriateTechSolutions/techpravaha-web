# Tech Pravaha website

Marketing and commerce site for Tech Pravaha, a design and build studio for things you launch: websites, apps, AI front-doors and growth automation. Every route is prerendered to static HTML; there is no runtime server.

**Before go-live, read [docs/MORNING-NOTES.md](docs/MORNING-NOTES.md):** accounts and secrets, content decisions, go-live order and known gaps in one checklist.

## Environment variables

Set these in `.env` locally and in the Cloudflare Pages project for production. They are inlined at build time, so changing one means a redeploy. The list is mirrored in `.env.example`.

| Variable | What it unlocks |
|---|---|
| `VITE_WHATSAPP_NUMBER` | Digits only with country code, e.g. `919876543210`. Turns every WhatsApp button into a `wa.me` click-to-chat link with a message naming the page or tier. Unset, those buttons fall back to `/contact`. |
| `VITE_GA_ID` | Google Analytics 4 measurement id (`G-...`). Loaded when the page is idle. Unset, GA is skipped. |
| `VITE_CLARITY_ID` | Microsoft Clarity project id. Keep masking on Balanced or Strict in the Clarity settings, or the privacy page stops being accurate. Unset, Clarity is skipped. |
| `VITE_BOOKING_URL` | Call-booking link (Google Calendar appointment page or Calendly). Unset, it points at `/contact` and the "Prefer a call?" block on `/contact` is hidden. |
| `VITE_API_URL` | Base URL of the `techpravaha-api` Worker that creates Razorpay orders, reports order status and takes contact-form leads (`POST /leads`, which appends to the Leads tab and pings the founder). Unset, it is `https://api.techpravaha.com`. If the Worker is unreachable the form shows the WhatsApp/email fallback. |
| `VITE_RAZORPAY_KEY_ID` | Razorpay public key id (`rzp_test_...` or `rzp_live_...`). Only switches online payment on; Checkout.js uses the key id the Worker returns. Unset or the placeholder, `/checkout/*` shows the price and a WhatsApp fallback instead of the Pay button. |

Leads no longer have a site env var: `VITE_LEADS_SCRIPT_URL` is gone, and the Apps Script URL now lives only on the Worker as `SHEETS_WEBHOOK_URL`. Never commit real secrets. Any new env var goes into `.env.example` with a dummy value in the same commit.

## Changing prices

`catalogue.json` at the repo root is the only price source. The site, the pricing page, the JSON-LD offers and the WhatsApp messages all read it.

1. Open `catalogue.json` on GitHub and edit the `price` (rupees, ex-GST), the `depositPct` (share charged at checkout, 1 to 100; absent means 100) or the `includes` list of a tier. No other file needs to change: the chat's facts (`workers/techpravaha-api/src/prompt-data.json`) are regenerated by the Worker deploy in step 4.
2. Commit to a branch and open a pull request. CI (`.github/workflows/ci.yml`) runs typecheck, the unit tests and the build on every pull request; the catalogue tests check structure (integer prices, `from` on quote tiers, badges), and every amount the suites expect (`tests/catalogue.test.ts`, `tests/checkout.test.tsx`, the Worker's `test/catalogue.test.ts` and `test/orders.test.ts`) is computed from `catalogue.json`, so a price edit needs no test change. `tests/price-parity.test.ts` checks that the site and the Worker charge the same amount for every buyable tier.
3. Merge. Cloudflare Pages rebuilds and redeploys in about a minute.
4. Redeploy the Worker. It bundles `catalogue.json` and the chat facts when it is deployed, so until then it still charges, and the chat still quotes, the old amount. On `main`, `.github/workflows/deploy-worker.yml` does this whenever `catalogue.json` or `workers/**` changes (it needs the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` repo secrets). By hand: `npm run worker:deploy` on Node 22 (it runs `npm run prompt:data` first, so the chat facts match the catalogue being deployed).

The real gate is the build: `npm run build` imports the catalogue, which runs `validateCatalogue` (unique ids, integer prices, a price on every buyable tier, a `from` on every quote tier, non-empty includes). A bad file fails the build, so the deploy fails and the previous version stays live. Make the CI check required on `main` in the GitHub branch settings so a red PR cannot merge.

A tier id on a lead (`?tier=`) must exist in the Worker's bundled `catalogue.json` too: `POST /leads` refuses an unknown tier with a 400, so the form falls back to WhatsApp for it. After adding a tier, redeploy the Worker (`.github/workflows/deploy-worker.yml` does this on merge to `main`).

The site and the Worker can disagree for a while: Pages and the Worker deploy separately, and a Worker that was not redeployed keeps the old prices. Checkout guards against that: it compares the Worker's order amount with the amount the page shows and refuses to open Razorpay when they differ (the buyer sees "Nothing was charged", "This price was just updated on our side" and the WhatsApp link, and GA gets a `checkout_mismatch` event). Nobody is charged a different amount, but that tier cannot be bought until both are deployed. Prices display ex-GST with a "+18% GST" note.

## Adding content

### A work item

1. Add an entry to `WORK` in `app/content/work.ts` (slug, name, one-liner, what shipped, stack, timeline, services, images).
2. Put screenshots in `public/work/<slug>/` and list them in `images`.
3. `scripts/lib/paths.ts` scans `work.ts` for `slug: '...'`, so the `/work/<slug>` page is prerendered and added to the sitemap with no other change.
4. Only real work, named with the client's permission.

### A lab app

1. Apps go in `public/lab/play/<slug>/index.html`. They are served as static files; there is no `/lab/:slug` route.
   An app must not call a third-party API from the browser (no AI API keys, no data leaving the page). `tests/content.test.ts` scans every lab HTML file and fails on known AI API hosts, a `fetch` to an outside host, or any other fetch target than `/lab/complete`.
   Apps that need a language model (Landlord Translator, Excuse Engine, Split the Awkward) call the Worker's `POST /lab/complete` with `{ app, input, options? }` and get back `{ text }`. The Worker holds each app's system prompt (`workers/techpravaha-api/src/lab-prompts.ts`) and calls Anthropic with `ANTHROPIC_API_KEY` (secret), model `LAB_MODEL` (default `claude-haiku-5-5`; Claude 4.x ids get a per-app temperature, newer ids get thinking off), output capped per app (1,200 tokens for Landlord Translator, 600 for the other two), 30 requests per IP per minute (`LAB_RATE` binding). Unknown apps or option shapes get a 400; no key gives 503, quota 429, model failure 502, and a refusal or an answer cut at the token cap 200 `{ text: "" }`, so each app falls back to its own offline or error state. Logs carry lengths and status, never the text. The proxy does not check `Origin` (CORS only stops other sites' browsers reading the reply), so its cost is bounded by the per-IP binding plus the spend cap on the Anthropic workspace.
   These files are served as-is by Pages, so the API host is not inlined at build time: each reads it from `<meta name="tp-api" content="https://api.techpravaha.com">`. If the Worker host changes, edit that tag in all three files (without it they call the relative `/lab/complete`); `public/_headers` caches `/lab/play/*` for 24 hours, so a change can take up to a day to reach returning visitors. Each file's header comment names its source; the only change from the source is the fetch target.
2. Add `play('<slug>', 'Name', 'One-sentence blurb.', ['tag', 'tag'])` to `LAB` in `app/content/lab.ts`.
3. Extensions and web apps without a public listing keep `href: '#'` until a store or hosted URL exists. Only unlinked extensions show "source on request".

## Hosted products

HomeFind, GoodFind and Plot Twist are served from the site root as static builds: `techpravaha.com/homefind/`, `/goodfind/`, `/plot-twist/`. Their files live in `public/<slug>/` and are committed, like the lab apps. Pages serves static files before anything else, so these paths never reach the React app. The slugs are `HOSTED_APP_SLUGS` in `scripts/lib/paths.ts`: postbuild adds `HOSTED_APP_PATHS` to the sitemap (not to the prerender list) and fails if an app's `index.html` has no `<title>` or meta description; the modulepreload strip (`PRELOAD_SKIP_DIRS`) and the placeholder gate skip them.

To update one, edit its repo, then run `npm run apps:build` here (or `npm run apps:build -- homefind` for one app) and commit the changes under `public/<slug>/`.

| App | Source repo | Build |
|---|---|---|
| HomeFind | `~/Documents/ChatGPT/Extensios/homefind` | `tsc -b`, then `vite build --base=/homefind/`. No patches: vite-plugin-pwa registers `/homefind/sw.js` with scope `/homefind/`, and the manifest uses relative URLs. |
| GoodFind | `~/Documents/ChatGPT/Extensios/goodfind` | `tsc -b`, then `vite build --base=/goodfind/`, then patches for root paths the base flag cannot reach (listed below). |
| Plot Twist | `~/Documents/ChatGPT/Fun/plot-twist` | Copied as-is (no `drafts/`, no `tests/`, no `README.md`); it only uses relative paths. It lives only at `/plot-twist/`; `public/_redirects` sends old `/lab/play/plot-twist/*` links there. |

What `scripts/apps/build-apps.ts` does:

- Builds into a temp directory, never into the source repo's `dist/`. The source repos are read-only; the only files a build writes there are `tsc` build-info caches under `node_modules/`. HomeFind's `npm run icons` step is skipped because it rewrites PNGs committed in that repo.
- GoodFind patches, each asserted to match exactly once so a source change fails the build: `register("/sw.js")` in the bundle becomes `register("/goodfind/sw.js",{scope:"/goodfind/"})`; the hand-written `sw.js` caches `/goodfind/`, `/goodfind/manifest.webmanifest` and `/goodfind/icons/goodfind-mark.svg` instead of root paths; its activate step only deletes caches named `goodfind-*` (it used to delete every other cache on the origin, which would include HomeFind's); the manifest `start_url`, `scope`, icons and shortcut URL move under `/goodfind/`; source maps are dropped.
- Adds a header comment to each `index.html` naming the source repo, commit, build date and base path, and adds a title or meta description only if the source has none.
- Fails if `index.html` links a root path outside `/<slug>/` or any file names an AI API host. `tests/content.test.ts` re-checks the committed files, including each service worker's scope.

`public/_headers` caches `/homefind/assets/*` and `/goodfind/assets/*` for a year (hashed names) and sends `no-cache` for each app's `index.html` and `sw.js`, so updates reach installed copies on the next visit. All apps share the techpravaha.com origin, so their `localStorage` and IndexedDB sit beside the site's; they use their own key and database names.

AfterBuy is not hosted. Its framework (vinext 1.0.0-beta.5, Next.js on Vite) can export static files at the domain root, but an export with `basePath: '/afterbuy'` renders no pages, and the app hardcodes root paths in its service worker, manifest, preview iframe and worker registration. It needs a subdomain or a source change; see `docs/MORNING-NOTES.md`.

### A journal post

1. Create `app/content/journal/YYYY-MM-DD-<slug>.md` with frontmatter:

   ```
   ---
   title: Post title
   date: 2026-10-10
   summary: One sentence for the list page, the RSS feed and meta description.

   ---
   ```

2. Write the body in Markdown (`##` headings, internal links like `[pricing](/pricing)`).

Add a real entry to `TESTIMONIALS` in `app/content/testimonials.ts`, transcribed verbatim (Upwork review or a message the client agreed to share). Never write or improve a quote. The section renders only when there are two or more entries; the file ships empty on purpose.

## Quality budget (as of 2026-10-10, phase 1 final run)

Lighthouse CI, mobile preset, 3 runs per page, asserted on the median run (`aggregationMethod: median-run`, not best-of-3). Budget: performance at least 0.90, SEO 1.00, accessibility at least 0.95, best practices at least 0.90.

| Page | Performance | Accessibility | Best practices | SEO |
|---|---|---|---|---|
| `/` | 0.92 | 1.00 | 1.00 | 1.00 |
| `/services/websites/` | 0.97 | 1.00 | 1.00 | 1.00 |

Individual performance runs in that autorun were 0.91 to 0.95 on `/` and 0.93 to 0.97 on `/services/websites/`. Performance varies by about 0.1 between single runs (simulated mobile throttling); earlier runs the same day ranged 0.88 to 0.99. Accessibility, best practices and SEO were stable. If a run misses, re-run before treating it as a regression. These numbers pre-date the phase 2 checkout and thanks pages, which are `noindex` and not in the LHCI set; re-run `npx @lhci/cli autorun` after a change that touches the shared bundle.

`scripts/postbuild.ts` strips the `modulepreload` links React Router adds to every prerendered page (outside `assets/`, `lab/play/` and the hosted products). They are about 350 KB of scripts that compete with CSS and fonts on slow mobile links; without them mobile FCP went from 3.6 s to 2.1 s. The module script still hydrates the page. Postbuild fails if any page still carries one.

## Phase 2 · Commerce

**Architecture.** The site stays static. A Cloudflare Worker (`workers/techpravaha-api`, plain `fetch` handler, no framework) owns every secret. `/checkout/<tierId>/` (prerendered for each buyable tier) collects name, email and phone, calls the Worker, and opens Razorpay Checkout.js; Checkout.js is loaded only when the buyer presses Pay. The Worker prices the order itself from `catalogue.json` (the client never sends an amount), creates the Razorpay order and stores it in KV. After payment Razorpay calls the Worker's webhook; once the signature checks out the Worker marks the order paid (idempotent on the payment id), appends a row to the "TP Orders" Google Sheet through an Apps Script web app, and emails the receipt through Resend. `/thanks/?order=<id>` polls the status endpoint and only says "confirmed" once the Worker reports `paid`. Quote-only tiers keep `/contact?tier=<id>`; with `VITE_RAZORPAY_KEY_ID` unset, checkout shows the price and a WhatsApp fallback.

**Worker endpoints** (CORS limited to `ALLOWED_ORIGINS`):

| Endpoint | Request | Response |
|---|---|---|
| `POST /orders` | JSON `{ tierId, customer: { name, email, phone, company?, gstin? }, page? }`. Unknown keys, or a quote-only or unknown tier, get a 400. | 200 `{ orderId, amount (paise charged now, GST included: the deposit for a tier with depositPct below 100), currency: "INR", keyId, tier: { label }, service: { name } }`. 400 `{ error, fields? }`, 502 provider error, 500 could not save. |
| `POST /webhooks/razorpay` | Razorpay's `payment.captured` event, signed with `X-Razorpay-Signature` (HMAC-SHA256 over the raw body). | 400 on a bad or missing signature, 413 on a body over 64 KiB. Otherwise 200 `{ ok: true }` (also `duplicate`, `unknown` or `ignored` variants), including when the Sheet or email step fails (an alert goes to `ALERT_EMAIL`). 500 only when KV fails before the payment is recorded, so Razorpay retries. |
| `GET /orders/:id/status` | Razorpay order id (`order_...`). | 200 `{ status: "created" or "paid", tierId, tier, service, amountPaise (charged now), totalPaise (full order), depositPct }`, never customer data. Read with a 30 s KV edge cache. 404 for unknown or malformed ids, 503 if KV is down. |
| `GET /health` | None. | `{ ok: true, version }` |

**Site environment variables** (Pages env; inlined at build, so changing one means a redeploy):

- `VITE_API_URL`: Worker base URL. Unset, it is `https://api.techpravaha.com`.
- `VITE_RAZORPAY_KEY_ID`: public key id (`rzp_test_...`, later `rzp_live_...`). Unset or the placeholder, online payment stays off.

**Worker secrets** (`wrangler secret put <NAME>`, never in git): `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `RESEND_API_KEY`, `SHEETS_WEBHOOK_URL`, `SHEETS_WEBHOOK_TOKEN`.

**Worker vars** (`wrangler.toml` `[vars]`, committed): `ALLOWED_ORIGINS`, `FROM_EMAIL`, `ALERT_EMAIL`; optional `BOOKING_URL` and `WHATSAPP_NUMBER` for the receipt email. Local dev reads dummies from `workers/techpravaha-api/.dev.vars` (copy `.dev.vars.example`; it is gitignored). Also needed before a deploy: the `ORDERS` KV namespace ids in `wrangler.toml`.

**Deploy.** Follow `docs/ops/razorpay-setup.md` in the go-live order below. The Worker needs Node 22 (`cd workers/techpravaha-api && nvm use`, or `export PATH=/opt/homebrew/opt/node@22/bin:$PATH`); the site and CI stay on Node 20. `wrangler deploy --dry-run` builds the bundle without a login or real KV ids. After the first manual deploy, `.github/workflows/deploy-worker.yml` redeploys the Worker on every push to `main` that touches `catalogue.json` or `workers/**`.

**Growth tiers: 50% deposit.** The four buyable Growth tiers carry `"depositPct": 50` in `catalogue.json`, so checkout charges 50% of the GST-inclusive total ("Charged now: ₹X (50% deposit)", "Balance at launch: ₹Y"). The receipt and the Orders Sheet show the deposit and the balance due at launch; the balance is invoiced by hand at launch. To take full payment instead, remove `depositPct` (or set it to 100) and change the "50% at checkout, 50% at launch" copy in the catalogue, Terms, Refunds, the pricing FAQ and the service FAQs in the same commit.

**Go-live order** (the same list is in `docs/ops/razorpay-setup.md` and the phase 2 plan's morning notes):

1. Razorpay, test mode: test keys, the test webhook (`payment.captured`, its own secret), auto-capture on, and the account's registered website includes `techpravaha.com`. If the account is shared with ATS, expect an "unknown order" alert for every ATS payment: webhooks are account-wide.
2. Resend: verify `techpravaha.com`, create the sending key.
3. Apps Script: deploy the orders script against the "TP Orders" Sheet; copy the `/exec` URL and the token.
4. Cloudflare: KV namespaces (ids into `wrangler.toml`), the six secrets with the **test** keys, Workers Logs on (`[observability]` in `wrangler.toml` or the dashboard), `npm run worker:deploy` on Node 22, the `api.techpravaha.com` route, the WAF rate limit on `POST /orders`, and a Workers plan whose KV write allowance covers the traffic (Free allows 1,000 writes a day).
5. Growth decision: the 50% deposit is implemented; keep it, or switch to full payment as described above.
6. Test-mode walkthrough on a Pages preview (below), with the test key in the Preview environment only.
7. After KYC: live keys and the live webhook secret on the Worker (`wrangler secret put`, then redeploy), then the ₹1 Payment Link check (`docs/ops/razorpay-setup.md` section 7).
8. Production Pages environment: `VITE_RAZORPAY_KEY_ID=rzp_live_...`, then redeploy the site.
9. Optional: buy the cheapest tier once for real and refund it. Then announce.

**Test-mode walkthrough** (go-live step 6, on a Pages preview, never on production):

1. The Worker runs with Razorpay **test** keys and the test webhook pointed at `https://api.techpravaha.com/webhooks/razorpay`.
2. In the Pages project, set `VITE_RAZORPAY_KEY_ID=rzp_test_...` (and `VITE_API_URL` if not the default) in the **Preview** environment only, never Production, and deploy a preview branch.
3. Add the preview branch origin (for example `https://<branch>.<project>.pages.dev`) to `ALLOWED_ORIGINS` in `wrangler.toml` and redeploy the Worker. Without it the browser blocks the call (CORS) and checkout says "Checkout did not open", with nothing in `wrangler tail`.
4. Buy Launch on `/pricing`: card `4111 1111 1111 1111`, any future expiry and CVV, then Success on the test bank page. Buy a Growth tier by UPI `success@razorpay` and check it charges the 50% deposit.
5. Once, open the Razorpay window, close it without paying, then press Pay again and pay. Razorpay must show the same order (no second order in the dashboard), and it must confirm normally.
6. Check: `/thanks` confirms, usually within a minute and up to two; the status endpoint says `paid`; one Orders Sheet row per payment; one receipt email per payment; no alert email. `docs/ops/razorpay-setup.md` section 5 has the full list.
7. Afterwards: remove the preview origin from `ALLOWED_ORIGINS` and redeploy the Worker, and delete the test rows from the Orders Sheet.
8. Browser e2e (optional, keeps the payment manual): start the Worker with `npm run worker:dev` on Node 22, with `.dev.vars` holding the Razorpay test keys and `ALLOWED_ORIGINS=http://localhost:4173`. Build the site against it, then run the spec, which fills the form on `/checkout/websites-launch/`, presses Pay and expects the Razorpay iframe within 15 s:

   ```bash
   VITE_API_URL=http://localhost:8787 VITE_RAZORPAY_KEY_ID=rzp_test_... npm run build
   E2E_RAZORPAY=1 VITE_API_URL=http://localhost:8787 npm run test:e2e -- checkout
   ```

   `VITE_*` values are inlined by `npm run build`, so they must be set on the build line (the same variable on the test line is harmless, the spec does not read it). Without `E2E_RAZORPAY` the spec skips itself.

## Phase 3 · Hooks

For visitors who are not ready to buy: a site chatbot, a free teardown lead magnet, internal pings to Yogesh for every order and lead, and the three lab apps that need a model, all through the same Worker. Every model call goes through the Worker; the site holds no model key.

**Chat.** A floating launcher (bottom right, 44px target, `aria-label="Chat with Tech Pravaha"`) mounts after hydration and an idle callback and never auto-opens. The `Chatbot` panel is a lazy chunk: it loads on the first hover, focus or click on the launcher, so it is never in the home page's critical path. If the chunk fails to load, a small "The chat could not load" panel takes its place, with "Try again" (fetches the chunk again, no reload) and the contact link. Replies render as plain text (never HTML or markdown), the transcript lives in `localStorage` (`tp-chat`, last 12 turns sent), and every answer can end in WhatsApp or `/contact`. The system prompt (`workers/techpravaha-api/src/prompt.ts`) is built from `workers/techpravaha-api/src/prompt-data.json`, which `npm run prompt:data` generates from `catalogue.json` and `app/content/services.ts`; it carries the price guard, the prompt-injection guard and the plain-text rule. The Worker sends the conversation to Anthropic's Messages API (`CHAT_MODEL`, default `claude-haiku-5-5`) with thinking off at effort `low`, no sampling parameters and a 600-token reply cap; a refusal or an empty answer gets the friendly fallback reply, an answer cut at the cap is trimmed to its last full sentence, and a reply that quotes a rupee amount not in the facts is replaced with a pointer to /pricing. `.github/workflows/deploy-worker.yml` regenerates the JSON before every Worker deploy (it also runs when `app/content/services.ts` changes), so a catalogue edit needs no manual step; `tests/prompt-data.test.ts` checks the generator and the checked-in file's structure (every service, every buyable tier with a price), not byte-equality. Run `npm run prompt:data` yourself only to see an edit in `npm run worker:dev`.

**Teardown lead magnet.** `/teardown/` takes a site address, name, email and an optional WhatsApp number and sends a `lead_magnet` lead through `POST /leads`; `/services/websites/`, `/services/design/` and the home page link to it. Delivery is manual in v1: each `lead_magnet` row in the Leads tab needs a reply within two working days (the success copy promises that).

**Leads and pings.** The contact form and the teardown form both POST to the Worker. The Worker answers 202 straight away, then appends a row to the Leads tab of the "TP Orders" Sheet (the Apps Script routes rows by `type`) and pings Yogesh. Paid orders ping too. A ping goes to Telegram when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are both set. Without Telegram, an order ping goes to `ALERT_EMAIL` through Resend, and a lead ping is skipped: `/leads` is open to anyone, so it must not spend the Resend quota that receipts depend on. Lead pings need Telegram; the Leads tab is the record. Pings never throw and never block the response.

The visitor sees "sent" on the 202, before anything is stored. A lead whose Sheet append fails is not stored anywhere else: the "Lead sheet append failed" alert says so, and the Telegram ping (name, email, page, and the site URL for a teardown) is all that is left of it. The message and phone are lost, so ask the visitor again.

**Lab proxy.** `landlord-translator`, `excuse-engine` and `split-the-awkward` (static files in `public/lab/play/<slug>/`) call `POST /lab/complete` on the host in their `<meta name="tp-api">` tag. The Worker holds a fixed system prompt per app, the model (`LAB_MODEL`, default `claude-haiku-5-5`) and the output cap. Without `ANTHROPIC_API_KEY` it answers 503 and each app shows its own offline state.

**Worker endpoints** (phase 3; CORS limited to `ALLOWED_ORIGINS`, logs carry ids, lengths and status, never message text):

| Endpoint | Request | Response | Limits |
|---|---|---|---|
| `POST /chat` | `{ messages: [{ role: "user" or "assistant", content }] }` | 200 `{ reply }`. 429 and 502 also carry a friendly `reply` the panel shows with the WhatsApp link; 400 on a bad body. | 20 messages, 2,000 chars per message, 64 KiB body; `CHAT_RATE` 12 per IP per minute; 10 s upstream timeout |
| `POST /leads` | `{ type: "contact" or "lead_magnet", name, email, message, page, phone?, tier?, order?, url? }` | 202 `{ ok: true }`; 400 `{ error, fields? }`; 429 | 16 KiB body; `LEADS_RATE` 6 per IP per minute |
| `POST /lab/complete` | `{ app, input, options }` (per-app options; unknown keys refused) | 200 `{ text }`; 400; 429; 502; 503 when `ANTHROPIC_API_KEY` is unset | 4,000 input chars; 600 output tokens (1,200 for the landlord translator); `LAB_RATE` 30 per IP per minute; 15 s timeout |

The three limits are Workers Rate Limiting bindings in `wrangler.toml` (`[[ratelimits]]`): nothing to create in the dashboard, counted per Cloudflare location and approximate.

**Worker secrets** (phase 3, `npx wrangler secret put <NAME>` on Node 22): `ANTHROPIC_API_KEY` (chat and lab apps; unset, `/chat` answers 502 with the outage reply and `/lab/complete` answers 503; see Anthropic key below), `TELEGRAM_BOT_TOKEN` (required for lead pings; see Telegram setup).

**Worker vars** (`wrangler.toml` `[vars]`): `TELEGRAM_CHAT_ID` (required for lead pings), `CHAT_MODEL` (optional, default `claude-haiku-5-5`; leave the default: the chat request sends thinking disabled at effort `low`, which another model may reject; the reply cap is 600 output tokens), `LAB_MODEL` (optional, default `claude-haiku-5-5`; leave the default). Local dev reads dummies from `.dev.vars` (`.dev.vars.example` lists them all).

**Anthropic key.** One `ANTHROPIC_API_KEY` serves the chat and the lab apps (Worker secret) and the journal drafts (the repo Actions secret of the same name, Phase 4). Create it in an Anthropic workspace with a monthly spend cap before go-live: the cap is a prerequisite, because `/chat` and `/lab/complete` are open to anyone and the per-IP limits are approximate. Confirm the chat model answers on your key with one request in the chat route's shape (expect a JSON body with `"type":"message"`; a `"type":"error"` body names the problem):

```sh
curl -s https://api.anthropic.com/v1/messages -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01" -H "Content-Type: application/json" -d '{"model":"claude-haiku-5-5","max_tokens":64,"thinking":{"type":"disabled"},"output_config":{"effort":"low"},"messages":[{"role":"user","content":"hi"}]}'
```

**Site env.** No new `VITE_*` variable: chat, leads and the teardown form all use `VITE_API_URL`.

**Telegram setup.** Message `@BotFather` on Telegram, send `/newbot`, and copy the token into `npx wrangler secret put TELEGRAM_BOT_TOKEN`. Send your new bot any message, open `https://api.telegram.org/bot<token>/getUpdates` in a browser, and copy `message.chat.id` (a group id starts with `-100`). Put it in `wrangler.toml` as `TELEGRAM_CHAT_ID` and redeploy the Worker (`npm run worker:deploy`, which regenerates the chat facts first). Until both are set, order pings arrive as emails and lead pings are skipped, so Telegram is a go-live prerequisite.

**Deploy order.** Publish the new Apps Script version (it routes `type: "lead"` rows to the Leads tab) before deploying the Worker: an old script would put leads in the Orders tab. Then set the secrets, deploy the Worker on Node 22 with `npm run worker:deploy` (it runs `npm run prompt:data` first, so a hand deploy never ships stale chat prices), and deploy the site.

## Phase 4 · Journal automation

A weekly pipeline drafts one journal post from a topic queue, runs a house-voice check, and opens a pull request. Nothing is published until you merge it, and nothing is posted to social: the captions are copy for you to paste.

**How it works.** `.github/workflows/journal-draft.yml` runs `scripts/journal/draft.ts`. It takes the first `queued` topic in `content/journal-topics.json` (or the one named by `--slug`), asks Claude for a draft (title, summary, tags, body and three captions), and lints it. If the lint passes, it writes `app/content/journal/<date>-<slug>.md` and `content/social/<slug>.md` (LinkedIn, X and WhatsApp status captions) and marks the topic `drafted` in the queue. The workflow runs in two jobs: `draft` (read-only token) installs, drafts and lints; `publish` (write token, installs nothing) commits those three files on a `journal/<slug>` branch, opens a PR titled "Journal: <title>" and dispatches the `CI` workflow on that branch. The PR body (`scripts/journal/pr-body.ts`) shows the word count, the lint result, the three captions and a review checklist, so you can review without opening files. Merging to `main` deploys the site through Cloudflare Pages, and the sitemap and RSS pick the post up. The workflow never commits to `main`.

**Schedule.** The job only runs on `main` (`if: github.ref == 'refs/heads/main'`); a manual dispatch from another branch is skipped. Every Monday at 03:17 UTC (08:47 IST), cron `17 3 * * 1` (off the hour, because GitHub delays or drops more scheduled runs at the top of the hour). Run it by hand from the Actions tab: "Journal draft" then "Run workflow", with an optional `slug` (draft that topic instead of the next queued one) and `date` (publish date, `YYYY-MM-DD`; default today in UTC). An empty queue exits cleanly with no PR. If a PR is open for the topic's `journal/<slug>` branch, the run emits a warning annotation and finishes green before the paid call. If the branch is on `origin` with no open PR (a closed draft, or a run whose PR step failed, for example because the Actions PR setting was off), the run fails red before the paid call with "A draft branch exists but no PR was opened": open the PR with `gh pr create --base main --head journal/<slug>` (keeps the paid draft), or delete the branch with `git push origin --delete journal/<slug>` to draft that topic again.

**Secrets and settings.** Add the repo Actions secret `ANTHROPIC_API_KEY` (Settings, Secrets and variables, Actions). It is used by the drafting step only and is never shipped to the browser. Also enable Settings, Actions, General, "Allow GitHub Actions to create and approve pull requests", or `gh pr create` is refused. A PR opened with the built-in token does not trigger the `CI` workflow, so for every journal PR the publish job runs `gh workflow run ci.yml --ref journal/<slug>` (`ci.yml` accepts `workflow_dispatch`, and a dispatch made with the built-in token does start a workflow; the job has `actions: write` for it). That run reports on the PR's head commit, which should satisfy a required `CI` check; confirm it on the first journal PR. If the dispatch fails, the job fails after opening the PR: run the same command yourself, or close and reopen the PR.

**Adding topics.** Append an object to `content/journal-topics.json`: `slug` (lowercase letters, digits and hyphens), `title` (90 characters or fewer), `angle` (the brief the model writes from: what the post argues and what it covers) and `status: "queued"`. Topics are drafted in file order.

**Where facts come from.** Two places, both in the brief the model receives (`scripts/journal/prompt.ts`, `buildUserPrompt`; see it with `--dry-run`): the topic's title and angle, and a package list built from `catalogue.json`. For each buyable tier the list gives the price before and with 18% GST, the GST on the price, the timeline (`weeks` or `days`), the `payment` line, the deposit share and both halves in rupees where `depositPct` is set, and the `includes` list. The model is told not to invent statistics, client names, prices or package items, and to take package details only from that list. The lint backs the numbers up (below): a rupee amount or a percentage may appear only if the catalogue implies it or the title or angle states it. Anything else factual (what a package does for a client, an outcome, a claim about the market) carries no number for the lint to catch, so it is a review item.

**What the lint enforces** (`scripts/journal/lint.ts`; one problem fails the run and writes nothing): no em-dashes or en-dashes, none of the superlatives on the voice blocklist (`scripts/lib/voice.ts`), 400 to 700 words in the body, title, summary, tag and caption length limits, rupee amounts (with a leading ₹, Rs or INR, or a trailing rupees, Rs, INR, thousand, lakh or crore, including `60k rupees` and `20,000-rupee`) only from the catalogue (prices, starting prices, GST totals, the GST on each price, amounts due at checkout and the balance due at launch) or the brief, percentages only 18% and 9% (GST, CGST and SGST), the catalogue's `depositPct` values (50 today) or one the brief states, links only to this site and no raw HTML, a body of `##` headings, paragraphs, lists and links only (no other heading levels, rules, code, tables or images), no client names unless the topic brief names them, and a frontmatter round-trip through the same parser the site uses.

**Run it locally.** `npm run journal:draft -- --dry-run` prints the chosen topic and both prompts and makes no API call. A real run needs `ANTHROPIC_API_KEY` exported in your shell (the script does not read `.env`): `npm run journal:draft -- --slug <slug> --date 2026-10-19`. Add `--summary /tmp/s.json` to also write the JSON summary the workflow reads, and `npm run journal:pr-body -- /tmp/s.json` to preview the PR body.

**If marking the topic drafted fails.** The post and sidecar are already on disk but the topic is still `queued`, so a re-run refuses to overwrite them. The error names the recovery: set that topic's `status` to `"drafted"` in `content/journal-topics.json` by hand, or delete both files and re-run.

**If a run fails.** A lint failure or script error fails the job, opens no PR and uploads the `journal-summary` artifact: the summary (when there is one) and, on a lint failure, the full draft as `journal-summary.draft.json`, so a one-word problem can be fixed by hand (write the post and sidecar, set the topic `drafted`, open the PR yourself) instead of paying for a re-run. Nothing is committed and the topic stays `queued`, so the next run tries it again, and every topic behind it waits: if a topic keeps failing the lint, edit its angle or move it down the file. The `drafted` status exists only on the `journal/<slug>` branch until its PR merges. While that PR is open, the next run sees it and exits green before the API call (a warning in the run log). To abandon a draft, close the PR and delete its branch: `main` still has the topic `queued`, so a later run drafts it again (a paid call). If the stale branch is left behind, the guard sees it on `origin` and fails the run before the paid call, every week, until you delete the branch or open a PR for it. To retire the topic instead, set its status to `published` or remove it from the queue on `main`.
